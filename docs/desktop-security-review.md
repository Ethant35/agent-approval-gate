# Desktop security review

Author: Ethan.

## Scope and result

Read-only review of `src/desktop.ts`, the additive desktop changes in `src/server.ts`, `scripts/build-desktop.mjs`, `native/main.swift`, `docs/native-launcher.md`, and the desktop core/update tests. The review focused on operator-token handling, readiness validation, child lifecycle, workspace/profile separation, version backups, and authorization coverage.

The browser and mediated-action paths reviewed here do not provide a way to launch the desktop child or obtain its operator capability without human policy authorization. The app now gives each gateway process a random in-memory operator bearer, separate from the persistent `human.token`, and the native host clears the WebKit session after an unexpected child exit. The child pipe still does not authenticate its parent process; I found no in-scope browser or mediated-action route to exploit that local-process boundary.

## Remaining boundary

### Residual boundary: the child pipe does not authenticate its parent process

`src/desktop.ts:73-75` rejects TTY stdin/stdout but does not verify that the caller is the signed AppKit launcher. A caller that can launch the bundled entry with pipes can receive that child session's random `operatorToken` in the `ready` line (`src/desktop.ts:153-155, 206-216`) and use it against the child's loopback server. The token is now separate from the persisted `human.token`, so capturing this pipe does not disclose the persistent credential, and it expires when that child server stops.

The test harness intentionally does this: `tests/core/desktop.test.mjs:9-24` spawns `dist/desktop.js` with three pipes and reads `ready.operatorToken`; it also checks the ephemeral token differs from the persistent token and that a restarted session rejects the old token (`tests/core/desktop.test.mjs:47-55, 120-127`). Direct launch therefore remains supported for trusted tests and local tools. A second launcher already holding the lease prevents a duplicate session, but a caller that can start its own session has no native-consent check.

Existing safeguards protect against a browser-only or remote caller: the token is not placed in HTTP responses or URLs, WebKit injects it only at the exact loopback origin into a nonpersistent session, navigation is same-origin, API writes require the operator bearer and explicit intent, and the desktop server binds to `127.0.0.1`. The native page has no URL scheme handler or script-message bridge. The gateway command policy starts with an empty command list; commands require an exact human-managed allowlist. The macOS executor uses a deny-default Seatbelt profile with workspace-limited file access and no network grant, so a mediated command cannot use the launcher to read app-support state or connect to the gateway.

This is a residual local-process boundary, not a demonstrated browser or mediated-command escape. The project constraints exclude arbitrary hostile code running as the same macOS user; such a process already has the operating-system access of that user and may read the 0600 persistent token directly. The pipe must therefore be described as private transport for the trusted native parent, not as proof of parent identity. Cross-user processes lack access to the private app-data directory and have no token path through the WebView. No in-scope route to invoke the desktop executable without the human command allowlist was found.

The previously reported startup-exit race is addressed in the current source. `GatewayProcess.isReadyAndRunning` checks both process liveness and shutdown state; startup checks it after readiness and again before creating the dashboard (`native/main.swift:94, 943, 965`). Unexpected termination during the busy startup phase is queued rather than discarded, then drained after startup (`native/main.swift:1023-1027, 1079-1082`). The controlled native self-test kills the tutorial child immediately after readiness, verifies that this dead child is not given a WebKit page, then uses the stopped-state recovery path to restart and continue the tutorial (`native/main.swift:947-962`; `docs/native-launcher.md:34`). I found no remaining lost-exit condition in this path. The parent reports the injected-exit self-test green; I did not rerun it independently.

## Other reviewed controls

- The native launcher validates the readiness type, token shape, literal loopback host, HTTP scheme, port, URL credentials/query/fragment/path, canonical workspace identity, and that the canonical state directory is a child of the private app-data root (`native/main.swift:262-297`). Workspace identity also receives a backend check against the stored policy (`src/desktop.ts:156-168`). I found no off-origin readiness acceptance in this path.
- The WebKit script is document-start and main-frame-only. It checks the exact origin before storing the token in `sessionStorage`. The website data store is nonpersistent and cleared on session stop. The dashboard has no native message handler or command bridge. CSP and navigation delegates block off-origin content, popups, and downloads.
- EOF on the child’s private stdin closes the server and releases the workspace lease. The native parent closes stdin on stop, switch, and quit, then uses bounded TERM/KILL fallback. The desktop backend also checks for parent EOF during startup. Existing generic lease recovery tests cover killed gateway processes; the hidden native self-test covers post-start child termination and restart, but not forcibly killing the native parent.
- App data, workspace profiles, and tutorial workspaces use separate directories. The backend rejects overlapping app-data and selected-workspace paths, binds only to loopback, validates that the persisted policy belongs to the selected canonical workspace, and serializes same-profile sessions with a native lease. Tutorial sessions use fresh directories beneath the app-data root.
- Version changes back up existing SQLite/token state before starting the current server, reject downgrade against a newer profile, and update profile metadata only after successful startup. The update test uses actual 2.0.0 state and restores the produced backup into the old CLI. I found no update/backup ordering race in the reviewed code.
- The build script bundles the qualified Node runtime and production dependencies with lifecycle scripts disabled, compiles the arm64 AppKit host with warnings as errors, and marks the artifact unsigned. Signing, notarization, and release validation remain separate gates as documented.

## Coverage and limits

The desktop core tests exercise the real child protocol, token shape and rotation, separation from the persistent token, old-token rejection after restart, unauthenticated endpoint denial, wrong-principal and wrong-origin rejection, actual approval/write, isolated tutorial replay, workspace policy/history persistence, and old-version backup/rollback. The native hidden self-test exercises both the injected startup-exit path and post-start child termination, along with WebKit-injected context, unauthenticated denial, tutorial and selected-workspace approvals, returning history, popup blocking, off-origin navigation, session-token clearing, and restart. The browser `desktop-ui` tests simulate the native bootstrap and are not evidence of WKWebView or AppKit behavior.

There is no negative native test for malformed readiness JSON, off-origin readiness, a fake parent process, or forcibly killing the native parent while the desktop child is active. This review reran the `operator-ui` Playwright project after narrowing its parameters selector; all 7 tests passed in 6.7 seconds. The parent reports the updated native startup-exit self-test green; I did not rerun the desktop core tests or native self-test independently. Signing/notarization and other hosts are not assessed here.
